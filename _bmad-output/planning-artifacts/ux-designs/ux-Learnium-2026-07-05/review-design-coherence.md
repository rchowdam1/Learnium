# Design Coherence Review — Learnium DESIGN.md

**Verdict:** The system is disciplined and mostly holds together — three radii, a clean 4pt scale, and reserved elevation are internally consistent — but the *central promise (lime = rewards only) is not enforceable as written*, and dark mode has two real structural soft spots: the inverted white CTA has no white token, and elevation + navy-emphasis both compress toward invisibility on pure black.

## Findings

| Severity | Location | Issue | Fix |
|---|---|---|---|
| **HIGH** | `components.progress-bar` / `progress-ring` / `lesson-node.active` / `level-badge` / leaderboard promotion / Colors §Accent Lime | **Lime reservation is not "rewards only" — it is "gamification + all progress," and progress visuals are always-on.** Daily-goal ring, Set%/Path% bars, active-node ring+glow pulse, level-ring, and promotion top-border all render lime persistently. Ambient lime is on nearly every screen at rest, so the discrete reward burst (XP pill, celebration glow) does not stand out from it. The stated goal "never spend the reward color / make wins feel ordinary" is self-contradicted by the spec itself. | Split the role: ambient/always-on progress tracks use a *desaturated* lime or navy fill; reserve saturated `accent` + `accent-glow` strictly for the moment of gain (XP award, correct, level-up, completion). Or drop the "reward feels earned" framing and rename the reservation "lime = gamification/progress." As written the discipline is unenforceable. |
| **HIGH** | `components.button-primary` (frontmatter note) + dark color set | **Dark inverted CTA has no white-fill token, and the note is wrong.** Note says dark `= {colors.background-dark}` "inverts to white fill" — but `background-dark` is `#000000` (black). No pure-white token exists in the dark set (`text-primary-dark` is `#F5F7FA`, near-white; `on-brand` `#FFFFFF` lives only in the light set). The most important button in dark mode resolves to an undefined value. | Add an explicit token (e.g. `on-brand-dark-surface: '#FFFFFF'` or a shared `pure-white`) and reference it for the dark primary fill. Fix the misleading comment. |
| **MED** | Frontmatter `components:` vs DESIGN §Components / EXPERIENCE | **Used-but-undefined component tokens.** ~9 referenced keys — `nav-top-bar`, `nav-mobile-bottom-bar`, `lesson-node`, `leaderboard-row`, `review-session-card`, `celebration-overlay`, `toast`, `level-badge`, `progress-ring` — are described in prose but absent from the `components:` frontmatter, so `{components.*}` refs won't resolve. (`.memlog` line 24 already flags this.) | Promote all referenced components to frontmatter keys with their token refs before handoff. |
| **MED** | All buttons, both modes | **Interactive-state matrix incomplete.** No `disabled` background token for any button (only `text-disabled` for text). Dark primary hover is prose ("slight dim"), not a token. Lime button disabled state unspecified. | Define `disabled` fill (both modes) and a real dark-primary-hover token; specify disabled for lime/secondary. |
| **MED** | Colors: `surface-raised` `#FFFFFF` == `background` `#FFFFFF` (light) | **Raised surfaces don't lift over the background in light mode.** `surface-raised` only lifts off the *tinted* `surface` (`#F7F8FA`); a card/input/modal placed directly on the white background is white-on-white, distinguished by hairline border alone. Dashboard cards sitting on background get zero tonal lift. | Either tint `surface-raised` slightly, or make the rule explicit: raised surfaces must sit on `surface`, never on `background`, in light mode. |
| **MED** | Colors dark: `surface-dark #0C1116` vs `surface-raised-dark #141B22` | **Dark elevation steps are compressed** (~8/channel, ≈3% luminance). Raised vs surface is near-indistinguishable without the border; the "tonal lift without shadow" claim mostly fails in dark and leans entirely on `border-dark`. | Widen the raised step (lift `surface-raised-dark` a few points) or acknowledge that dark elevation is border-only and drop the tonal-lift claim for dark. |
| **MED** | `brand-dark #3E5C74`; nav-mobile active tab | **Navy collapses as an emphasis color in dark.** `brand-dark` is a muted slate that doesn't pop on black, and the dark primary CTA is white (not navy). Tellingly, the mobile active-tab tint is already swapped to `text-primary-dark` in dark *because navy won't read* — so navy's "the brand color / emphasis" role largely disappears in dark, carried by white + lime instead. | Accept and document that navy is logo/header-only in dark and emphasis is white/lime; or brighten `brand-dark` enough to actually function as emphasis. Don't claim co-equal navy emphasis across modes. |
| **MED** | Typography `display` (Bricolage) vs `numeral` (Space Grotesk); `celebration-overlay` | **Font ambiguity when a heading contains a number.** Celebration headline is `display` (Bricolage) but the numeral rule forces *all* gamified numbers into Space Grotesk tabular — so "Level 6" either mixes two fonts mid-line or breaks the numeral rule. | Add a precedence rule: numerals inside `display`/`display-sm` headlines stay in the display font (numeral rule applies only to standalone counters/metrics), or vice-versa — pick one explicitly. |
| **LOW** | Colors: `warning`, `brand-hover-dark`, `accent-glow-dark` | **Orphan/underused tokens.** `warning` (amber) is defined but no component uses it (streak uses `streak`; toasts use success/error/info). `brand-hover-dark` isn't referenced (dark primary hover is "slight dim", not brand). | Prune or assign an owner; if reserved, mark as such. |
| **LOW** | Typography (3 families) | **Load-performance note.** 3 families × 2 weights ≈ 6 files, incl. the less-common Bricolage Grotesque, on a mobile-first product. Because numerals are tabular (layout stability is the whole point), FOUT/CLS is a real risk. | Preload the two above-the-fold families, `font-display: swap`, subset (Latin + lining/tabular figures). |
| **LOW** | Buttons | **No tertiary/ghost button defined.** Hierarchy is primary(inverted) + secondary(outline) + lime(special). Adequate for now, but any "quiet" action (e.g. "Skip", "Maybe later") has no token and will get invented ad-hoc. | Add a `button-tertiary` (text/ghost) token proactively. |

## Notes on what is coherent (no action)

- **Radius** (`xl`/`2xl`/`full`) — consistent, no contradictions; toast/card/input all `xl`, modal/celebration `2xl`, pills/rings `full`.
- **Spacing** — 4pt scale clean; no rogue values in component specs.
- **Elevation policy** — flat + hairline, shadow reserved for modal/popover/celebration/toast; applied consistently.
- **Inverted CTA vs surface-raised card adjacency** — the hypothesized clash is *not* a real risk: dark primary is pure white `#FFFFFF`, `surface-raised-dark` is `#141B22` (very dark gray); the contrast gap is large, no confusion. (The real dark-CTA problem is the missing white token — see HIGH above.)
