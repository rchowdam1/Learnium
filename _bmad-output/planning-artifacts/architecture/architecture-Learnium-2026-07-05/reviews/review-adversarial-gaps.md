# Adversarial Architecture Gap Review

Reviewed artifact: `ARCHITECTURE-SPINE.md`

Verdict: **Needs revision before downstream implementation split.** The spine correctly names the major authority boundaries, but several adopted decisions still leave enough ambiguity that two teams could obey every AD and produce incompatible implementations. The highest-risk gaps are not missing topics; they are underspecified ownership contracts, event contracts, and operational contracts.

## Findings

- **Quota ordering is internally contradictory enough to create divergent implementations.** AD-3 says the action sequence is `check quota atomically -> validate input -> call generator/RAG/provider -> validate output -> persist durable result -> decrement quota atomically`, while also saying quota loss on rejected/failed actions must be prevented. One team could implement a "reserve before provider call" RPC, another could implement "decrement after persistence", and both would claim compliance. The spine must bind whether quota is checked, reserved, consumed, released, or expired, and whether provider cost failures are billable to the user.

- **The phrase "one mutation owner" does not name the owner.** AD-3 says quota counters have one mutation owner "preferably database RPCs", but "preferably" leaves room for route-local updates, server action helpers, or RPCs. Two downstream units could both avoid read endpoints mutating quota and still create incompatible set/chat quota mechanics. The spine should make quota mutation RPCs mandatory or name an explicit domain service as the sole owner.

- **Billing state has no required event matrix or idempotency contract.** AD-7 states Stripe webhooks update Supabase tier/quota fields, but the Stripe event matrix and API version pinning are deferred. That lets one unit implement `checkout.session.completed` as the unlock event while another waits for `customer.subscription.updated`; one could treat cancellations immediately and another at period end. Both obey "webhook-confirmed state" but diverge on entitlement. The spine should bind the canonical subscription lifecycle events, idempotency key, customer mapping, and period-bound entitlement semantics.

- **Quota and billing ownership overlap but are not reconciled.** AD-3 owns counters, AD-7 owns subscription state, and the Deferred section leaves quota numbers/fair-use open. A billing unit could update `profile.is_subscribed` and reset quotas in webhook handlers, while a quota unit could reset based on its own tier reads in scheduled jobs. The spine needs a single derived-entitlement model: what Stripe writes, what quota RPCs read, and whether webhooks ever mutate remaining counters directly.

- **RAG schema mirroring is explicitly manual, so drift is permitted by design.** AD-6 says request/response schema changes are mirrored manually between Next.js and Python. Two teams can obey this by updating their local caller/service manually and still ship incompatible names, error envelopes, cache flags, or streaming behavior. The spine should require a canonical contract artifact, generated types, contract tests, or at least a versioned JSON schema checked by both sides.

- **RAG ownership is tied to `buddyId`, but the trust boundary is not specified.** AD-6 blocks browser calls to arbitrary `buddyId`, and AD-14 says the server mediates upload, but it does not bind how RAG proves that a Next.js request is authorized or same-tenant. One implementation might rely on network-private deployment; another might add service tokens and signed ingestion requests. Both obey the ADs, but only one protects cross-tenant vector poisoning if the sidecar is exposed or misrouted. The spine should bind service-to-service auth, accepted caller identity, and whether RAG ever trusts raw object ids.

- **RAG readiness states exist but transition ownership is incomplete.** AD-14 names `pending_db`, `pending_rag`, `ready`, and `failed`, but not the durable table/field owner, legal transitions, retry idempotency key, cleanup behavior, or whether chat is blocked for non-ready buddies. Two units could implement the same states with different transition semantics and user-visible behavior. The spine should bind the lifecycle state machine and the invariant that only `ready` buddies can answer chat.

- **Generated content validation is underspecified despite being mandatory.** AD-5 requires schema, quality, safety, and input-language checks, but does not define the quality floor, language source of truth, reportable identity shape, AI disclosure location, or whether unsafe content is stored in `flagged` only or never persisted. Two generator units could both pass "minimum quality checks" with incompatible validators. The spine should bind the validation contract and where validation failures are recorded.

- **Generated content atomicity allows two incompatible persistence strategies.** AD-15 allows either a transactional database function or compensating cleanup path. Those are not equivalent operationally: one can guarantee no partial graph; the other depends on cleanup reliability and observability. Two units could choose different strategies for Sets, Paths, and Review banks, making failure handling and retries inconsistent. The spine should either mandate transaction-first for Postgres-owned graphs or define a shared compensation protocol with cleanup status and retry semantics.

- **Ownership proof is required but the canonical join path is not bound.** AD-12 says object ids must prove ownership through parent `profile_id`, but does not specify the required ownership chain for `quizId`, `lessonId`, `chatId`, Review items, Path sets, or League membership. One unit might check quiz ownership through `quiz -> lesson -> set -> profile`, another through a denormalized `profile_id`, and another through RLS. All could comply while producing different query patterns and authorization bugs. The spine should define canonical ownership paths per object type or require database policies/functions that encapsulate them.

- **Social privacy has ambiguous consent semantics.** AD-8 says public/social reads use privacy-limited projections "only when the user has consented or the feature requires cohort participation." That "or" is a loophole: one League team can treat participation as consent by default, while another requires explicit opt-in. Both obey the sentence. The spine should bind defaults, consent records, opt-in/opt-out behavior, historical data removal, and whether share cards are public, unlisted, or authenticated.

- **League opt-out behavior is self-contradictory for users who leave cohorts.** AD-8 says opt-out users neither appear nor see standings, while AD-11 says weekly League cycles are scheduled jobs. It does not say what happens to existing weekly XP, promotion/demotion, rewards, or historical standings when a user opts out mid-cycle. Two League units can produce incompatible fairness/privacy outcomes. Bind opt-out timing, retroactive removal, reward eligibility, and audit retention.

- **Operations authority is named but not made deployable.** AD-11 requires server-side job entrypoints with idempotent run keys, but the spine defers test/CI shape and does not name the scheduler mechanism, lock strategy, retry policy, or observability surface. One team could use Vercel Cron, another a Supabase scheduled function, and both would comply while duplicating or racing weekly cycles and quota resets. Bind the job runner, lock table/key format, retry semantics, and run audit table.

- **Account deletion/export is mapped to AD-11 but lacks data ownership rules.** FR-21..FR-23 map billing/account deletion to scheduled jobs, yet the spine does not bind deletion order across Supabase auth, profile rows, Stripe customer records, RAG vectors, semantic cache entries, public projections, and generated content. Two downstream units could delete profile data but leave vectors/cache, or delete auth first and orphan records. The spine should define deletion/export ownership and mandatory teardown targets.

- **Service-role use is isolated but privileged module boundaries are unnamed.** AD-10 says service-role access is restricted to server-only privileged modules, but does not name those modules or allowed operations. A future unit could put service-role helpers under `lib/admin.ts` for deletion/profile creation, another under route handlers for billing repair, and both claim "server-only". The spine should bind an allowlist of service-role modules and operations, with regular user-facing queries forbidden from importing them.

- **API response conventions are too weak for cross-unit clients.** The convention allows `{ success: true, ... }` or `{ success: false, message }`, but existing and future routes can still differ on HTTP status, `error` vs `message`, committed-state payloads, and retryability. Two downstream units can comply and still force UI-specific error handling. The spine should bind error taxonomy, status-code conventions, and retryable/non-retryable flags for provider, validation, quota, auth, and readiness failures.

## Decisions The Spine Should Bind

- Mandate quota RPCs or a named quota domain service; define check/reserve/consume/release semantics.
- Define Stripe webhook event matrix, entitlement states, idempotency, and the exact boundary between billing updates and quota resets.
- Require a versioned RAG contract plus service-to-service authentication and explicit tenant authorization.
- Define canonical ownership chains or database authorization functions for every user-owned id.
- Specify Buddy ingestion lifecycle transitions, retry keys, cleanup behavior, and chat gating.
- Define generated-content validation criteria, failure recording, AI disclosure placement, and transaction/compensation policy.
- Replace social/privacy consent ambiguity with explicit opt-in defaults, opt-out semantics, and public projection tables or views.
- Bind scheduled-job runner, lock/audit model, retry behavior, and operational ownership for quota resets, leagues, reminders, review scheduling, and deletion/export.
